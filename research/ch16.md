## 2. The concept as the field holds it

**What "calling another language" means today.** For a working programmer, reaching another language from the one you write means a foreign function interface or a child process: a call into a shared library, or a run of an interpreter whose output you parse. Notebook environments and polyglot virtual machines make the same move with more comfort. (General knowledge; the record holds no dated study of these tools. The estate's own study says so itself: "The field's polyglot tools were described from the genre, not re-read" — `drafts/stzsite-roots-and-achievements.md`, 12.28, "Not measured".) The field's default is that the door is open and unguarded: whatever the other runtime can do, your process lets it do.

**What the estate's own field study says about the host as an escape.** Two sentences in one file pull in opposite directions, and the chapter needs both.
- On the way out: "The host language is the escape hatch, and the escape hatch is always taken." (`D:\GitHub\ringua\docs\landscape.md`, section 1.3, "founding analysis, 2026-08-06"; the examples there are Gradle and Chef, internal languages that "died of openness".)
- On the way in: "Lesson: the differentiator is escape. A language you make must be consumable from any stack" (same file, section 1.6, on Racket's `#lang`, "stalled at the border of its own world").
So the field's lesson is double: an escape that is open destroys a closed language, and a language with no way out dies at its own border. Softanza's answer in the record is one door, governed. The door is therefore not a convenience. It is the place where closure ends, and the vision says so: the "expert venue" is "One governed door per level, never a hidden escape" (`D:\GitHub\softanza\vision\06-ALPHABET.md`, "The two venues").

**What "supporting a language" means in the field, for the facet half.** Tools that let you write in the syntax you know over another engine (a transpiler, a language server, a second front end for one compiler) are the field's facets. (General knowledge.) The estate's design memo for them is blunt about the cost: "The honest promise of a second face is readability for a human who knows the other language, not behavioural transfer." (`D:\GitHub\ringpp\haro\CODEGRAPH.md`, section 5, "What it costs the claim", 2026-10-04.)

### Block 10 · a door that fails says so, and its trace says exit code 0 (the limit; marked: effects)
Claim (the limit, shown): at main the R door raises on every call, because its generated script is not valid R. And the call trace records exit code 0 for a call that failed. Status: **ran; evidence for section 8**. This needs R 4.5.1 at the default path; on a machine without R the first line printed would be a different failure.

```haro
oStat = new stzExterCode(:R)
oStat.SetCode("res <- c(1, 2, 3)")
bRaised = 0
try
	oStat.Execute()
catch
	bRaised = 1
done
? bRaised
#--> 1
? oStat.CallTrace()[1][:exitcode]
#--> 0
```
What the log said (in French on this machine): "unexpected symbol in ... _items_". The generated R script holds `_items_ <- lapply(...)` (from `$cRToRingTransFunc`), and an R identifier cannot begin with an underscore. I confirmed with `Rscript` on a one-line file (`_items_ <- 1`): the same error. The trace's `:Exitcode` is a literal `0` passed to `RecordExecution(_cLog_, 0)` in `Execute()`; failure is detected only by the absence of the result file. The same underscore names sit in the Python, Julia and NodeJS wrappers, where they are valid; the Prolog wrapper uses a lowercase `result` as a variable in clause heads, which in Prolog is an atom (read, not run, no Prolog here).
