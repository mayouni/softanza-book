## 2. The concept as the field holds it

Two things are held separately by the field, and the chapter joins them.

**The loop and what replaced it.** The field's answer to "do something to every item" has been the loop, then a sequence of named replacements that each hide one move of the loop. The ones a reader knows (general knowledge, years well established): the iterator object (Java 1.2, 1998); the list comprehension (Python, PEP 202, 2000) and the generator (PEP 255, 2001); language-integrated query (C# 3.0 with .NET 3.5, 2007); `map`, `filter` and `reduce` on arrays (ECMAScript 5, 2009); streams (Java 8, 2014). Each names a move: to traverse, to select, to transform, to fold. None names the four moves as one vocabulary. The record's own comparison of its walker with "Traditional Loops, Java Iterators, .NET Enumerators, Python List Comprehensions" is a table of 13 feature rows in `LIB\base\doc\narrations\stzwalker-beyond-loops-the -walker-metaphor.md` (section "Softanza Advantage"); it is undated and its cells are claims, not runs. A book may cite it as the author's argument; it must not present it as a measurement.

**The condition inside an argument.** The field passes a condition as a function (a lambda), or as a string in a small language that a host evaluates: the `WHERE` clause of SQL; path and filter languages for JSON (general knowledge); and, in the record's own account, the original Softanza form, a string handed to the host's `eval`. The record states why that form was left: "`eval()` is bad on two fronts: it is slow ... and unsafe" (`LIB\base\doc\narrations\stz-conditional-code-narration.md`, section "Two paths, one idea"). [Quote shortened; the sentence is longer in the file.] What a general-purpose list API rarely offers is the choice written into the name: a string path that cannot reach the host (W) and a function path that can (WF).

**The mental model.** The field's nearest practices are the rubber-duck problem statement, test-first development, and the "find, then act" idiom of query languages (general knowledge). None prescribes an order of questions about a value. The record does: contain, count, find, act.

### Block S2 · the condition is data, not code — KEPT

Claim: a W condition is compiled by the engine, never evaluated by the host. A call to a host function inside it neither runs nor raises: the condition simply matches nothing. Contrast with WF, which does run host code (run, not blocked: the same `print` inside a WF function printed "seen" three times). Sources: `LIB\engine\src\expr.zig` header ("Replaces Ring's eval() for Map, Filter, Reduce, FindW, and all ...W() functions"), narration `stz-conditional-code-narration.md` table ("Safe with untrusted input: yes ... cannot escape the sandbox" for W, "no" for WF), guard `338_w_function.ring` ("W() ... does not evaluate the condition; it simply packages the string").

```haro
o1 = new stzList([ 3, 8, 5, 12, 1, 9 ])
? @@( o1.FindW('{ @item > 5 and print("hacked") }') )
#--> [ ]
? @@( W('{ @item > 5 }') )
#--> [ "where", "{ @item > 5 }" ]
```

Run output: `[ ]` and `[ "where", "{ @item > 5 }" ]`, and nothing else: the word "hacked" was not printed. The author's point there is architecture: a goal-oriented design "is the only way one architect masters a project of this size" [the study's paraphrase of his statement; do not quote it as his words].

2. **The condition language replaced `eval`.** STUDY 12.6, row "Conditional code": then "`W` compiled with `eval()`, a `W`/`WXT` split for speed"; now "the engine's expression DSL, no `eval()`, plus `WF` for Ring functions; `WXT` deprecated"; verdict "improvement". The guard `483_w_and_wf_forms_in_conditional_code` says the same: "(The older ...WXT() 'extended' form is retired: W now does everything it did.)" Whose words: the library's session writing the guard; the narration is undated.

3. **The walker's edge rule is a design principle.** "Walking at the Edge" is told as a principle of "natural orientation and practical safety": before the start is an error, beyond the end is ignored (`LIB\base\doc\narrations\stzwalker-walking-at-the-edge-narration.md`, section "Natural Orientation"). The author's authorship is not stated in the file (the narration is in the style of a session's article; the site calls the narrations "the author's articles", STUDY 12.20). Treat as the library's design, not as a dated ruling.

4. **The mental model was kept as seven steps.** The course charter rules that "the course teaches the seven steps as written. Nobody renumbers the source narration" (STUDY 12.17, quoting the charter's finding F2, which reads the technical core as five: Select, Contains, Count, Find, Apply). Refused: renumbering. 5. **What was refused as grammar (from chapter 5's decision, for the writer's awareness):** names that tolerate a misspelling, parameters in any order, method names in other human languages (STUDY 12.16, Plan B). Not repeated here.

6. **The engine home of the metaphors is designed, not decided as built.** `SOFTANZA_ENGINE_DESIGN.md` marks Walker, Checker, Yielder, Performer "[PLANNED]" and states "The four metaphors form a complete interaction vocabulary" (line 609 onward); phase F+ "Checker/Yielder/Performer" is 3 modules, PLANNED (line 3563). ## 7. The field, and where it leads

Honest losses beside the wins, from the record and general knowledge.

- **Laziness.** A field iterator or generator produces the next item on demand and can be infinite. The walker builds "a 'map' of its entire potential journey the moment it is created" (the narration's own words, `...beyond-loops...md`, "The Walker Concept"). That is a win for foresight (you can ask `Unwalkables()` before moving) and a loss for a very large or endless traversal. The record does not discuss it; the site's Craft page repeats the foresight and not the cost.
- **Arbitrary code in the condition.** The field's lambda carries any logic. The W language is bounded on purpose: "call your own Ring functions or object methods ... mutate state" are things W "deliberately cannot do" (narration `stz-conditional-code-narration.md`, "What `W` deliberately cannot do"). The expression module's language, from its header: literals, `@item`, `@i`, `@accumulator`, `@numberofitems`, arithmetic, comparison, `and`/`or`/`not`, and a short list of functions (`isstring`, `isnumber`, `islist`, `len`, `lower`, `upper`, `abs`, `type`), 2,014 lines (`LIB\engine\src\expr.zig`). The price of the sandbox is the second path, WF, which is full host power and, by the narration's own table, "no" safe with untrusted input.
- **Silence on a mistake.** I ran a W condition with a foreign call and got `[ ]` and no error (block S2). A field lambda would fail loudly or run. That is a design choice with a risk: a typo in a condition and a condition that matches nothing look the same. The record does not state this; I measured it once, on one case.
- **Named operations versus lambdas.** The yielder class takes a name (`Map(:Abs)`, `Filter(:IsPositive)`, `Reduce(:Sum)`): readable, closed, and engine-backed ("All operations are engine-backed via the stz_yielder Zig module", `LIB\base\list\stzYielder.ring`, header). The field's `map(x -> ...)` is open. For an open transform Softanza uses `YieldW` or `YieldWF`.
- **Reach and tooling.** The iterators and comprehensions of the field are in every mainstream language, with editor support, type checking and an existing literature. The four metaphors exist in one library, in one language, with no tooling beyond it. (General knowledge; the record's own honest sections on the field are in STUDY 12.22, not read in full for this chapter.)
- **The record's own comparison table** (walker versus loops, Java iterators, .NET enumerators, Python comprehensions; 13 rows, all rated in the walker's favour) loses nothing on paper and is not a run. A book that prints it prints no loss. Do not reuse it.

## 9. Six doors

- **The programmer.** Ask the same four questions of any object, and when you reach for a loop, name which move it is making instead: walk, check, yield or perform.
- **The analyst.** Say the problem in plain words and the verbs you used are the steps: "are all of them", "which ones", "give me the big ones", "make them negative" are a checker, a find, a yielder and a performer.
- **The designer.** The yielder never changes the list, the performer does; the verb tells you which, so a design can say "this step is read-only" and mean it.
- **The decision-maker.** A condition is a string that the engine reads and cannot run as code; it can be stored, shown and approved. The price is a small language, and a mistake that stays quiet.
- **The educator.** The course already has the order: "Walk, ask, produce, act" is a chapter of the self-study book (`D:\GitHub\stzsite\content\en\education-self.md`), after "Find, then apply".
- **The agent.** Write the condition as the string, not as code; it cannot escape. When the answer is empty, check the condition's words before you trust the emptiness.

## 10. The exercise

Never answered first. Statement for the book:

Take the list `[ 4, 9, 12, 7, 20, 3 ]`. Four sentences are given: (a) "Are all of them above 2?" (b) "Give me, as a new list, those above 8, doubled." (c) "Make the ones above 8 negative, in the list itself." (d) "Which positions are 2, 4 and 6?" For each, say first which of the four moves it is (walk, check, yield, perform) and what you expect it to print, written under the line before you run. Then write the line, with the condition as a string wherever there is a condition. Run it. After (b) and (c), print the list again: say, before you look, in which of the two the list has changed.

Tutor's rule: the book gives no answer. A tutor checks two things only: did the learner name the move before writing the line, and does the promise under each line match the run.
