## 2. The concept as the field holds it

For the field, an IDE is the place where one language is edited, run and debugged, with a language service beside the editor
and extensions around it. Its chrome is stable and known: a title or identity bar, a side explorer, a main editing area, a
panel of problems or output, a status bar with the branch, the cursor position and the error count. Two of the field's choices
are the ones this chapter answers. First, the language service is a separate process behind a published protocol, so one
editor serves many languages (the Language Server Protocol, from Microsoft's VS Code, 2016; *general knowledge*, and the
record's own reading of it: "adopt LSP's separation, reject LSP's data model as the primary one", `D:\GitHub\ringpad\STUDY.md`, v1.0, 2026-08-12, §2).
Second, the assistant is a pane or a terminal beside the code, and the human approves its edits.

The record's own field studies, with dates, are three.
- **The host language's own notepad, measured.** The study measured the notepad that ships with the former host language at 33
  source files and 4,155 lines, seven dock widgets, a 15-key configuration and no language service: "it exists, it ships in
  the box, and it works on the day you install" (`D:\GitHub\ringpad\STUDY.md`, 2026-08-12, §1; read from the source on that machine).
- **The fast editors, from the ergonomics specification (v1.0, March 2026, `ZINCODE_ERGONOMICS_SPEC_v1_0.md`, Preface).** Zed: "input-to-screen < 16ms on any modern hardware. No exceptions", "minimal chrome", and "No status bar clutter, no toolbar forests"; Helix: "making state visible at every step", dry-run before a structural change; JetBrains: inspections that say why and offer a fix. The same file says, of Claude Code, "the Split Assistant shows the exact plan before executing a single operation" (the specification's own lesson, not a claim about that tool).
- **The status bar, as that specification wrote it (Part 6):** 24 px high, "carries only essential state", with five build states, among them `? unchecked`, "No build run yet (new project)", and `✗ 3 errors`. The state of "not yet judged" has its own word; a bar that was green by default would be the field's usual lie.

Where the field is silent, and the chapter answers: it orders its toolbars by the tool's features, not by the life of the
thing being made; and it lets an assistant's proposal land as an edit, with the human's approval as a habit. (General
knowledge, marked; the record's claim for its own pattern is in §3 and §5.)

## 9. Six doors

- **The programmer.** You write the shell as text, and a court tells you the one box that serves no verb before anything is drawn; the same file is a native window and a page, and the library has a page that says when they disagree.

- **The designer.** Your interface has a constitution of twenty-two verbs and a closed grammar that "adds renderings, never verbs"; every element must say which verb it serves, and the library already finds the ones that say none.
- **The decision-maker.** Ask of any environment three things: does its status bar read a court, does its assistant live in one panel and propose, and who judges that the two shells agree. - **The agent.** The shell is a text file you can read and write, the tree a screen reader reads is the tree you may read ("what a screen reader can operate, an agent can operate", Rule 104, in `stzAccessibilityTree.ring`), and your proposals appear in a rail and commit nowhere.
