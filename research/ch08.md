## 2. The concept as the field holds it

**Functions as linguistic expressions.** The field has two habits near this idea and no system. The first is
naming convention that carries meaning: Swift's API Design Guidelines (swift.org, 2016, with Swift 3) tell the
author to name by side effect, an imperative verb for the mutating method (`x.sort()`) and a participle for the
non-mutating one (`x.sorted()`), and to make call sites "read as English"; Python has the same pair as a habit
(`list.sort()` against `sorted()`); Ruby marks its mutators and predicates with `!` and `?`. (General knowledge,
well established; not read in the record.) These are conventions: nothing in the language checks them, and each
covers one or two forms. The second habit is the fluent interface, named by Martin Fowler and Eric Evans in 2005
(Fowler's bliki entry "FluentInterface", 20 December 2005; general knowledge): methods that return the receiver so a
line reads like a sentence. Named arguments (Python's keyword-only arguments, PEP 3102, 2006; Swift and Kotlin's
argument labels) cover a third form. What the field does not have is the whole set read as one grammar, where the
spelling of a name says voice, number, mood, negation, extent and which parameters it takes.

The record's own account of the field is thin here. The narration compares to no named tool, except two lines
about call sites: `arrayUtils.slice(array, 0, 10, false)` in JavaScript and a Qt `indexOf("e", 0, 3, 0)` call, both
used to show a call whose numbers and flags say nothing
(`base/doc/narrations/stz-functions-as-linguistic-expressions.md`, section "Function Suffixes"). The Haro
principles file gives the nearest measured field fact: no macros, no templates, no way to define a family of
functions from a rule (`D:\GitHub\ringpp\haro\PRINCIPLES.md` §7). The chapter should not claim that Softanza is
the only one with a grammar of names: §6 and §8 show that the grammar is checked only in part.

**Scope.** In the field "scope" means lexical visibility: where a name can be seen. The idea of this chapter is
different, and the field has its pieces without the name. A regular expression's meaning is bent by flags set
elsewhere: in PCRE2 the options `MULTILINE` and `DOTALL`, in JavaScript the flags `m` and `s` (added in ES2018),
in Perl the inline `(?m)` and `(?s)`; the record states the same problem in its own words
(`base/doc/deepdives/stz-regexp-confusion-solved-deepdive.md`: "The dot (.) behaves differently depending on flags").
Concurrency has the structured form: Kotlin's coroutine scope and "structured concurrency" (Roman Elizarov's essay,
2018), and Java's `StructuredTaskScope` (JEP 453, preview in Java 21, 2023). Memory has the borrow checker of Rust,
a scope of ownership and lifetime checked at compile time. (All general knowledge.) Each is a field-specific
answer: the frame is named, but in a different place and by a different mechanism every time. None of them says that
it is one cure for one disease.

## 3. The first principle

Two sentences, one per half. The forms half returns to the idea that the name is the meaning. The library's own
parser says it in a comment:

> "A Softanza method name is a COMPOSITIONAL linguistic expression ... the name IS the meaning."
> (`base/reflect/stzReflectFuncs.ring`, above `_StzParseName`)

The scope half is the sentence of the design document's section 1:

> "Make the operative scope explicit and first-class at the call site, so that behavior is decided by something you
> can see and name"
> (`base/doc/design/SCOPE_ORIENTED_PROGRAMMING.md`, §1; the sentence goes on: "and so that the library itself can
> reason about it")

The short form that ties the two is M4 of the same file, §3: "The scope is a semantic handle, not a comment." A form
is the same kind of handle: a suffix is something the library reads (block F2), not a comment on the name.
The tie to chapter 3 (declare, then govern) is that in both halves the frame is declared in the name and the library
governs with it.

## 7. The field, and where it leads

Forms.
- *The field leads in enforcement.* The Swift naming guideline is reviewed by a community and by tooling; Go and Python formatters run on every
  commit (general knowledge). In the library the forms are written by hand: Haro's analysis counted 46,493 definitions, about 10,600 of them
  "spelling variants of an existing base", 35 spellings of `find`, and "No macros, no templates, no compile-time code generation, and no way to

  re-measured by me; my narrower grep reads 36,868 `def` lines in `base/` outside test and archive).

  default, multilingual) and examples that answer otherwise (§4.1). The study says it plainly (12.6: "archived without a decision"; "documented,
  not guarded").
- *Where Softanza stands apart:* the forms are one grammar that the library itself decodes (F2) and that Haro generates and checks. No convention
  in Swift or Ruby is read back by a toolchain this way.

Scope.
- *The field leads in static enforcement.* Rust's borrow checker proves an ownership scope at compile time; structured concurrency in Kotlin and
  Java closes the lifetime of work in a block (general knowledge). The library's equivalent for memory is a candidate row only: "Memory ...
  {owned, borrowed, shared, arena, static}" in the document's §9 table, not built. Concurrency's instance is a plan.
- *The design's own caution, same document.* v1.2 says of instance four: "its M1-M5 mapping is design, and this note says so plainly" (header).
  §9: "four of the five are M1-M4 fields, not M5."
- *Where Softanza stands apart:* one cure named for a disease that recurs across unrelated fields, with the library computing from the scope (the
  placement plan resolves a capability against a target before a byte is built) and the scope reporting its refusal in words.

## 9. Six doors

  receiver, `QC` works on a copy; and write the scope in the verb, not in a flag set elsewhere.
- **The analyst.** Say the question in the verb's words (find, find all except, is not, count where) and let the line read back as your sentence; choose
  the scope (line, word, whole) as part of the question.
- **The designer.** A name is an interface contract: the past participle never changes the object; a refusal that names the scope ("scope 'esp32' (espidf)
  forbids 'process'") is an interface too.
- **The decision-maker.** The scope is the cheap place to decide: the plan shows, before a byte is built, which of four verdicts each capability takes on
  each target, and it says "nothing built yet". One line of risk: five forms of the founding article do not run today.
- **The educator.** Teach the verb's form first, then the scope; the course already draws the answer with `vizFind` (`11-draw-the-answer`); make the learner
  predict the verdict before the run.
- **The agent.** You will be corrected by the library, not by folklore: the explainer reads your method name back as a sentence, and a scope refuses what the
  target forbids at write time, on the laptop.
