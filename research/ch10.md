## 2. The concept as the field holds it

**The practice today.** In the field, to program is to write source text and to change it is to produce a diff. The unit
of work is the line, the commit, the pull request. A change is accepted when a person has read the diff, or when tests
pass, or when both do. When machines began to write the diffs the same unit stayed: the model proposes a patch, a person
or a second model reviews the patch, a pipeline gates it. The record's own account of the moment is a dated one: the
compass of 2026-09-25 records the Rails creator saying on 2026-09-23 that "writing code by hand is no longer an
economically viable skill" (`D:\GitHub\softanza\dashboard\CONCLUSIONS.md`, line 949, a second-hand quotation of a public
talk; the writer should cite the record, not the talk). If hand-writing is going away, what a person does with software
is decided elsewhere: choosing, bounding, reviewing, refusing. The word the industry uses for that is *review*, and its
tool is still the diff. The site states the problem in its lede: "the unit of work can no longer be 'the change'"
(`D:\GitHub\stzsite\content\en\refinement.md`, line 4, quoted in part).

**Three practices the field already has for the same trouble** (each marked general knowledge; dates are those I hold, the
writer should verify them before printing):
- *Plan, then apply* in infrastructure code: a tool prints what it will change before it changes it (Terraform's `plan`
  and `apply`, HashiCorp, first released 2014; general knowledge). It gives the preview, not the gate.
- *Admission control* in clusters: a request to change the system is judged by validating (and mutating) controllers
  before it is stored (Kubernetes admission controllers; dynamic admission webhooks reached general availability around
  2019; general knowledge). It gives the gate, not the typed proposal against a declared point.
- *Spec-driven development*: the specification is the durable artifact and the code is generated from it. The author's
  own first book names it as the nearest neighbour and marks the seam: "regeneration is the opposite of an audit chain"
  (`D:\GitHub\ayouni\books\refinement-book\manuscript\rop-manifesto.md`, line 2367, section 4 of its neighbours chapter).
  The same page says the disagreement is about what is durable: `Spec -> Code` "makes intent durable and the change
  ephemeral", and refinement "makes the *change* durable and governed" (same file, line 2367).

The same book makes a second distinction the chapter can use: some tools govern the *actor* (what an agent may spend or
touch, what tool it may call) and some govern the *change* (whether the thing that landed may stand). "Process and
consequence are different things to be answerable for" (same file, line 2385). The chapter's subject is the second.

## 9. Six doors

- **The programmer.** Mark the three or four values that may change (a rate, a threshold, an algorithm), give them bounds,
  and your next change is a proposal the gate answers in a sentence that names its stage, not a diff someone must read.
- **The analyst.** The rule that spans two numbers ("this rate never below that floor") is written once, as a rule on the
  point, and every later change is judged against it.
- **The designer.** The knobs of an interface are the natural refinement points; in the library today only code is built, the
  interface domain is the product's framing, so say it plainly and point to the interface constitution for the law.
- **The decision-maker.** "Who changed this, why, under whose authority, and can we go back" has a mechanical answer: the
  step is in the timeline with its posture; the decision is in the governance lineage; the return is one call.
- **The educator.** The tutor lets a learner propose a change and read the refusal; a refusal that names its stage is the
  lesson (this chapter's exercise).
- **The agent.** The design calls typed proposals against declared knobs "the SAFEST WRITE SURFACE they can be given"
  (design line 1381): discoverable (`RefinementPoints`), bounded, validated, reversible, and the origin is judged by the
  floor (`As(:llm)`). The gate "does not care who authored the proposal" (line 1384).
