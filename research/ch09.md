## 2. The concept as the field holds it

Three concepts meet in this chapter. Each has a field. Items marked "general knowledge" are not from the record; the writer
should check a date before printing it.

**Pattern bound to action.** The oldest form is the Unix tools: `lex` (Lesk and Schmidt, Bell Labs, 1975) and AWK (Aho,
Weinberger and Kernighan, 1977) are programs made of `pattern { action }` pairs run over a stream of text (general knowledge).
Production-rule systems extend the idea from text to facts: OPS5 and the Rete matching algorithm (Charles Forgy; the algorithm's
paper is 1982), CLIPS (NASA, mid-1980s), Drools in the Java world (general knowledge). The record knows this lineage and says so
without inflating it: the intelligence architecture calls the Regexuter "a nascent FORWARD-CHAINING RULE ENGINE" and says the
upgrade to fixpoint "turns it into production rules" (`SL/base/doc/design/SOFTANZA_INTELLIGENCE_ARCHITECTURE.md`, section 5.2,
lines 896-902; the header says "captured 2026-07-13 from the author's directive"). The study agrees (12.18): "What is new is
not the rule engine but the condition side ... and the provenance side."

**Reactive programming.** The field's vocabulary is the reactive-extensions family (Rx, begun at Microsoft around 2009-2010,
then RxJS, RxJava and others), the Reactive Streams specification with its **backpressure** (initiative 2013, version 1.0 in
2015, in the JDK as `java.util.concurrent.Flow` since Java 9) and the Reactive Manifesto (2013, revised 2014) (all general
knowledge). The record's own account of the field is the first section of the Reaxis article: "observables, subscribers,
backpressure, cold vs hot streams, schedulers", metaphors "borrowed from plumbing, telephony and publishing"
(`SL/base/doc/narrations/stz-reaxis-reactive-programming-narration.md`, section "The Language Crisis in Reactive Programming",
undated, the author's). The record's dated field study of the layer underneath is `REACTIVE_ENGINE_GAP_ANALYSIS.md`
(**2026-06-13**), which compares the engine with libuv, libcurl, nginx, Go, Tokio, Envoy and OpenTelemetry (see section 7).

**Time as a model, not a scalar.** The field's programming time is scalar: `datetime` in Python, `java.time`, Luxon in
JavaScript, which the record's own article describes as stopping at "representation and calculation"
(`stztimeline-temporal-design-philosophy-in-softanza.md`, undated). The field's reasoning about intervals is James F. Allen's
interval algebra (1983, thirteen relations between two intervals; general knowledge); the field's shortest path on a grid is A*
(Hart, Nilsson and Raphael, 1968; general knowledge), and the classic test `grid/18_testing_path_finding_algorithms.ring` itself
labels its path "A* algorithm (ShortestPath)".

### Rung 1: the Regexuter

**B1 · A trigger, a computation, a result** (alternate; the shortest). Source:
`SL/base/test/regexuter/04_processing_numbers_in_text.ring`; the same shape opens the narration. Ran: yes.
```haro
rxu() {
	AddTrigger(:NumberFound = "(\d+)")
	AddCode( :When = :NumberFound, :Do = '{ @value = @number(@value) * 2 }' )
	Process("The total was 42 dollars and 13 cents.")
	? @@( Matches() )
	#--> [ "42", "13" ]
	? @@( Results() )
	#--> [ 84, 26 ]
}
```
Output of the run: `[ "42", "13" ]` / `[ 84, 26 ]`. Claim: a pattern is bound to code; processing the text fires the code on every
match; the matches and the results are kept apart. (The code string must contain `@value`, else `AddCode` raises:
`stzRegexUter.ring` line 103.)

**B2 · The state, with its provenance** (recommended). Source: `SL/base/test/regexuter/07_matches.ring` (the narration's redaction
example), reduced to the fields that carry the claim, because the full state also holds a clock timestamp (my run printed
`08/10/2026 21:51:36`; never print it). Ran: yes.
```haro
rxu() {
	Trigger(:SensitiveData = "(password|secret|key):\s*(\w+)")
	@C(:When = :SensitiveData, :Do = '{ @value = "REDACTED-" + len(@value) }')
	Process("User credentials: password: abc123 secret: def456")
	? @@( Results() )
	#--> [ "REDACTED-16", "REDACTED-14" ]
	? @@( Positions() )
	#--> [ 19, 36 ]
	? State()[1][:matchedvalue]
	#--> password: abc123
	? State()[1][:computedvalue]
	#--> REDACTED-16
	? @@( State()[2][:dependson] )
	#--> [ "sensitivedata" ]
}
```
Output: `[ "REDACTED-16", "REDACTED-14" ]` / `[ 19, 36 ]` / `password: abc123` / `REDACTED-16` / `[ "sensitivedata" ]`. Claim: the
Regexuter reacts, and it remembers what it changed: the match, the value it computed, the position, the trigger that fired. The
state entry also holds `:timestamp`, `:computationorder`, `:pattern`, `:affects`. Here `:dependson` is the trigger itself (section 8:
that is all the "dependency chain" holds at main). The class source writes the keys in camel case (`:triggerName`); the run
prints them lower-cased (`triggername`, `matchedvalue`, ...).

**B3 · The cascade that does not cascade** (recommended; this is the block the task asks for). Mine, built on the architecture's own
sentence (quoted in section 8). Ran: yes.
```haro
rxu() {
	Trigger(:Number = "\d+")
	Trigger(:Big = "\d{3,}")
	@C(:When = :Number, :Do = '{ @value = @number(@value) * 100 }')
	@C(:When = :Big, :Do = '{ @value = "BIG" }')
	Process("Found 7 items")
	? @@( Matches() )
	#--> [ "7" ]
	? @@( Results() )
	#--> [ 700 ]
	? @@( Triggers() )
	#--> [ "number" ]
}
```
Output: `[ "7" ]` / `[ 700 ]` / `[ "number" ]`. Claim: the first trigger turned 7 into 700; the second trigger is written for numbers of
three digits or more, and 700 is one, yet it never fired. Every trigger is matched once against the original text
(`stzRegexUter.ring` line 151, `AllMatches(cText, _cPattern_)`), and what one trigger writes is not offered to the others. That is the
whole difference between rung 1 and rung 2. A real cascade would print `BIG` as a second result.

### Rung 3: the agent, where the cascade does run

**B5 · A cascade to fixpoint, at the agent level** (recommended). Source: `SL/base/test/agentic/piagent_narrated.ring`, scene 5 (three
skills chaining placed, cooking, plated, served; guard 14/14). I cut the block to two skills and no verification to keep it short; it is

```haro
oAgent = new stzPIAgent("cook")
oAgent.MemoryQ().Learn("order", "state", "placed")
```

### Reaxis

**B6 · A stream, in plain words** (recommended). Source: `SL/base/test/reactivestream/03_stream_transformations_-_map_filter.ring` and
the narration's first example (`Transform`, `Filter`, `OnPassed`), with `FeedMany` for the older spelling and the output collected, so the
page does not depend on printing from a callback. Offline; the loop ends by itself when the data is exhausted. Ran: yes.
```haro
aSeen = []
Rs = new stzReactiveSystem()
Rs {
	oStream = CreateStream("prices")
	oStream {
		Transform(func price { return price * 1.20 })
		Filter(func price { return price >= 100 })
		OnPassed(func item { aSeen + item })
		FeedMany([ 80, 90, 100, 120 ])
	}
	RunLoop()
}
? @@( aSeen )
#--> [ 108, 120, 144 ]
```
Output: `[ 108, 120, 144 ]`. Claim: Container (the system), Stream, Rfunction (the three `func` in waiting); 80 becomes 96 and is dropped by
the filter, 90 becomes 108 and passes. A first run with `? item` in the callback printed `108`, `120`, `144` on three lines.
Aliases to know (read in `SL/base/reactive/stzReactiveStream.ring`, lines 149-170): `Feed`, `FeedWith`, `Emit`, `Send`, `Receive` and the
older misspelling `Recieve` all call the same method; `FeedMany`, `FeedWithMany`, `SendMany`, `EmitMany`, `ReceiveMany`, `RecieveMany`
likewise. So "Feed replaces emit" is a naming choice, not a removal.

**B7 · Overflow, not backpressure** (recommended). Source: `SL/base/test/reactivestream/00_overflow_narrated.ring` (17/17 on my run),
with one strategy. Ran: yes.
```haro
oRs = new stzReactiveSystem()
```

## 7. The field, and where it leads

Honest sections, with dates; where the record is silent on a date I say so.

1. **Pattern-action and production rules.** The field leads in maturity: lex and AWK have been in daily use for decades; Rete-based engines match many
   rules against many facts efficiently, and the Softanzuter's rung 1 does not: it loops over the triggers and matches each pattern against the whole
   text (`stzRegexUter.ring`, `Process`, lines 124-175). The record's honest sentence (intelligence architecture section 5.2, 2026-07-13): "scaffolding
   anticipates cascading but does not yet RE-FIRE dependent triggers to fixpoint". What Softanza has that those tools do not: the condition side can be
   a sentence of any of six pattern languages over six media (12.4), and every firing keeps its provenance. The loss, printed: no cascade (B3), no
   shared state between a Regexuter and a Listexuter, no incremental matching.

2. **Reactive streams.** `REACTIVE_ENGINE_GAP_ANALYSIS.md` (2026-06-13) is the record's honest section for the layer under Reaxis. Selected verdicts, each
   under 25 words: against libuv, non-blocking I/O is a "Real gap" for the engine then (the document predates the vendored libuv of 2026-06-14,
   `TIER2_REACTOR_DIRECTION.md`); against Go, context and cancellation is "Critical for agentic -- no way to cancel a slow downstream call"; against Tokio,
   "Async/await models cooperative concurrency cleanly" and the engine's alternative "is workable but noisier"; against Envoy, retry storms "have killed
   more production systems than any other class of bug". What the field has that Reaxis lacks, from the article set itself: Rx's operator library is
   advanced (the library's own comparison grid, `softanza-reactive-objects-narration.md` lines 812-824, marks RxJS "Stream Processing: Advanced" and
   Softanza "Yes"); Reaxis has no reactive-streams-style demand signalling (a full buffer applies its overflow strategy, it does not push back on the
   producer); and I read no combine-latest or merge operators named. **Warning:** that same grid scores "Learning Curve" in stars, RxJS "Hard", Softanza
   "Easy", undated and uncited; it is the kind of grid chapter 3 distrusts (12.22). Do not reproduce it; cite the dated gap analysis.

3. **Time.** The record's own comparison is `stztimeline-temporal-design-philosophy-in-softanza.md` (undated): "Time should be modeled, not just measured."

## 9. Six doors

- **The programmer.** Write the trigger and the code beside it; the match, the result and the state come back as data you can print (B2). Stop writing the loop

- **The analyst.** Every firing keeps the value before, the value after, the position and the trigger: a log you can read with the same verbs as any other list

  not hidden. A grid draws itself in text (B11), so a reader can see the answer.

  which is which.
- **The educator.** The ladder is a curriculum in four steps (pattern, reflex, mind, agent), each with something a pupil can run (B1, B3, B5). The education skill
  PA-01 carries one sentence at its expert level, "builds a regexuter that reacts to what it recognises" (quoted by 12.18; I did not open the skill).
- **The agent.** The state and the decision log are for it: a thought is a state entry with its provenance; a refusal comes with its reason; `Pursue()` returns a
  count and the same call a second time returns 0 (B5), a fixpoint a program can test.

## 10. The exercise

Idea, judged by the tutor's rule (the learner predicts first; the page never gives the answer before the learner has written theirs):

Two triggers over one text, the second written for numbers of three digits or more, the first multiplying a number by one hundred. Before running anything, the
reader writes in one sentence what `Results()` will hold and how many triggers will have fired. Then they write two promises in the form of ch3: the line the
library prints today, and the line a Softanzuter that cascaded to a fixpoint would print. They run the first. They do not try to make the second pass.

```haro exercise
rxu() {
	Trigger(:Number = "\d+")
	Trigger(:Big = "\d{3,}")
	@C(:When = :Number, :Do = '{ @value = @number(@value) * 100 }')
	@C(:When = :Big, :Do = '{ @value = "BIG" }')
	Process("Found 7 items")
	? @@( Results() )
	#--> what you think the library prints
	#--> what a cascading Softanzuter would print
}
```
(The first promise is B3's second line, `[ 700 ]`; the exercise keeps it back. A harder variant: change the second trigger so that it matches the text and not the
result, and predict the order of the results.)
